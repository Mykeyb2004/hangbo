# 多周期满意度计算可行性评估

评估日期：2026-10-11。本文只评估计算口径及实现要求，未修改单周期生产代码、原始数据和已有工作簿。

## 判断

用户的业务目标成立：若多周期满意度定义为“各计算周期等权的平均表现”，多周期应先得到各期满意度，再汇总各期结果。当前直接合并问卷重算的算法仍可用于“合并样本的指标评分”，但不能代表上述周期等权口径。

建议将“单周期评分”和“多周期汇总”作为不同的计算策略，复用单周期的指标和分类规则，不重新发明每道题的评分方法。多周期可以读取既有单周期结果，也可以从合并原始表按周期划分后逐期评分。

需求有一个必要限定：**如果同时要求所有单元格都是对应分期值的简单平均、行列总分又全部按当前空值忽略规则做简单平均，则通常无法同时成立。** 当前实际数据已经构成反例。

## 当前数据的直接验证

1–2 月是一个独立计算周期，与 3–9 月合计八期。

| 汇总顺序 | 未四舍五入结果 | 两位小数 |
| --- | ---: | ---: |
| 先得到各期表底总分，再平均八期 | 9.708750 | 9.71 |
| 先将每个客户类型在有值周期中平均，再等权平均18个客户类型 | 9.716484 | 9.72 |
| 按每期客户类型实际权重构建贡献，再汇总贡献 | 9.710571 | 9.71 |

第三项基于各期客户类型两位小数分数，在各期表底总分四舍五入之前进行计算。它与第一项的精确差额为 -0.001821205755，来自各期表底舍入。当前显示均为9.71，但未来数据不能仅以“本次显示一致”作为精确关系保证。

因此，前一轮“平均各期总分即可得到9.71”的建议满足总体均值要求，但没有完整满足本轮增加的表内横纵关系要求。

## 为什么逐格平均不能自动对齐

用两个周期、两个客户类型的例子：

| 周期 | 客户A | 客户B | 周期总分 |
| --- | ---: | ---: | ---: |
| 第1期 | 10 | 无数据 | 10 |
| 第2期 | 8 | 6 | 7 |

周期等权总分为 `(10 + 7) / 2 = 8.5`。

逐格跨期平均后，A为9，B为6；再等权平均客户类型得 `(9 + 6) / 2 = 7.5`。

原因是第1期A占整期100%，第2期A和B分别占50%。跨期逐格平均后把A、B都赋予50%的累计权重，改变了既有周期总分的计算含义。

不能把无数据填成0分来处理。0分是实际评分，不代表缺少观测。

## 推荐方案：周期等权，层级贡献汇总

先让每期占累计结果的 `1/T`，其中T是所选计算周期数。保留各期内部实际使用的客户类型权重和指标权重，并沿计算层级汇总“得分贡献”和“权重”。

对客户类型i，令当期有效类型数为n_t，客户类型当期得分为S_ti。该客户类型在当期无有效分数时不产生权重或贡献。

```text
客户类型累计权重 W_i = SUM(1 / T / n_t)
客户类型累计贡献 C_i = SUM(S_ti / T / n_t)
客户类型累计得分 R_i = C_i / W_i
总体得分 = SUM(C_i) = SUM(W_i × R_i)
```

例子中A累计权重为0.75、累计得分为9.333333；B权重为0.25、累计得分为6。因此总体为 `0.75 × 9.333333 + 0.25 × 6 = 8.5`。

一级指标和明细题可沿相同方式递归汇总，使用各期实际参与的指标权重，得到可追溯的横向关系。酒店餐饮的组件聚合也须作为独立层级记录权重。这样无需修改原始评分或凭目标总分倒推调整系数。

代价是：多周期的客户类型分数、指标分数可能不再等于该行/该列有值周期的简单平均。它们应明确标注为按周期内贡献计算的加权得分，并展示权重或提供可见的计算明细。

## 横向表结构的约束

当前汇总表是展示映射，不是所有列互斥的完整评分分解。部分会展/会议客户的“餐饮服务”已经包含在“配套服务”中，随后又单独展示餐饮子项。直接将所有展示列平均会重复计入。

例如累计会议主承办的原始一级指标为会展服务9.90、硬件设施9.51、配套服务9.71、智慧场馆9.00，总分为9.53；汇总表额外展示餐饮服务9.10。餐饮子项不能作为第五个等权一级指标再次参与总分。

新多周期表应采用互斥的一级指标作为参与横向总分计算的字段，子项可标注为“其中：餐饮服务”供展示。如果将餐饮拆成独立一级指标，必须同时重新定义配套服务范围，并考虑这是否也改变单周期算法。

各列底部的“指标总分”还须定义：是沿全局层级权重计算的该指标加权得分，还是各期该列底部均值。两种统计量在有缺失项时也不必相同。建议用全局层级权重保证总体的横纵贡献闭合；如需各期列均值，可作为另外的趋势统计展示。

## 必须明确的实现要求

1. 总体口径：各计算周期等权，总分按所选各期总分平均得到。
2. 单周期来源：统一读取已发布报表，或统一按同版算法从原始数据重算。不能混用两种来源。1–2月历史产物差异见已有核查报告。
3. 表内关系：采用权重和贡献计算行列合计。若要求所有单元格为简单分期均值，只能把它们作为趋势展示，并另列贡献表，不能承诺按原公式行列闭合。
4. 缺失区分：不适用、当期无样本、该题无有效回答、整期数据缺失分别记录。整期应到而未到的数据不得静默删除并改变T。
5. 周期注册：显式列出所选周期，不把批次名称的月份跨度直接作为分母。2026年若1–2月仍合为一期，覆盖全年到12月时是11个计算周期；以后若1月和2月独立计算才是12期。
6. 精度：保存完整计算精度，最后格式显示两位小数。若必须精确等于既有两位小数周期总分的均值，保留可追溯的“舍入差额”。不能靠改某一客户分数消除差额。
7. 空白批次：T为实际选定的有效业务周期数，单期选择应退化为该期结果；季度、跨年和全年均按周期列表处理。
8. 验证：总分与周期均值一致，客户贡献和与总分一致，权重和为1，一级指标到类型贡献关系一致，并覆盖缺失客户类型、稀疏指标、酒店餐饮组件、重复周期与舍入边界。

## 技术可行性

总体均值要求：可行，已确认当前八期显示为9.71。

总体均值与横纵贡献关系同时成立：可行，需要引入明确层级权重、整理参与计分的展示字段、统一舍入策略。可以保留旧单周期算法并增加独立多周期汇总模块。

所有单元格简单平均、行列仍全用普通平均、沿用现有缺失规则，同时保证总体9.71：当前数据下不成立，不能作为开发验收条件。

9.71是当前数据的预期结果，不应写成固定常量。新增10–12月后应随数据和所选周期重新计算。

独立验证：

```bash
uv run python tests/verify_multi_period_feasibility.py
```

该脚本只读取现有八期汇总工作簿，验证平均顺序冲突、客户类型贡献权重及舍入差额。完整横向贡献方案尚属于设计要求，不代表已实现新多周期算法。
